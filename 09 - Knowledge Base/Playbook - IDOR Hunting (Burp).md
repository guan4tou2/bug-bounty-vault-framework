# Playbook - IDOR Hunting with Burp Suite Only

> "If I can guess it... I can probably access it." The essence of IDOR: the developer implemented **authentication** (are you logged in as someone) but forgot **authorization** (are you allowed to access this specific resource).

---

## Scope / When to use

IDOR occurs when:
1. The application returns a resource identified by an ID
2. It verified you are "some" logged-in user
3. But it **never verified** whether you're allowed to access the resource behind "that specific ID"

Use this playbook whenever you need a systematic, Burp-only workflow for finding IDOR across REST, GraphQL, and file-download endpoints — no specialized scanner required.

---

## Phases

### Phase 1: Setup

```
Burp Suite -> Proxy -> Options -> 127.0.0.1:8080
Firefox -> Network Settings -> Manual proxy -> 127.0.0.1:8080
```

- Enable Intercept
- Browse the target application normally (profile, orders, documents, messages)
- Let HTTP History accumulate requests

### Phase 2: Identify Attack Surface

In HTTP History, look for requests containing these parameter shapes:

```
# URL parameters
?id=123
?user_id=456
?account=789
?order_id=1234
?file=document.pdf
?document=report_123

# Path parameters
/api/users/123
/api/orders/456/details
/api/files/download/789

# POST body
{"userId": 123}
{"documentId": "abc-123"}
```

**High-value endpoint prefixes**:
- `/api/`, `/account/`, `/user/`, `/profile/`
- `/documents/`, `/download/`, `/export/`
- `/invoice/`, `/order/`, `/payment/`
- `/messages/`, `/inbox/`

### Phase 3: Manual Testing in Repeater

```
Right-click -> Send to Repeater
```

**Systematic ID-modification strategy:**

| ID type | Test approach |
|---------|----------------|
| **Sequential integer** | `123` -> `124`, `122`, `1`, `0`, `-1` |
| **UUID** | Use Account #2's UUID |
| **Username/email** | Swap in another user's identifier |
| **Filename** | `myfile.pdf` -> `../admin.pdf` or another user's filename |
| **Hash/token** | Use a hash/token generated by a different account |

**Response analysis:**

| Response | Meaning | Action |
|----------|---------|--------|
| `200` + another user's data | ✅ **IDOR confirmed** | Screenshot and record |
| `403 Forbidden` | Access control working correctly | Move on |
| `404 Not Found` | ID doesn't exist, or (possibly) the ID is being filtered | Retry with a real ID belonging to another user |
| `200` + empty data | Possibly filtered but no explicit error | Try other IDs |
| A generic "not found" exception type | Requires Phase 5's dual-account verification | Obtain another user's real ID |

### Phase 4: Advanced Techniques

#### 4a. HTTP Method Substitution

Developers often protect only GET and forget POST/PUT/DELETE:

```
Original: GET /api/user/123
Try:      POST /api/user/123
          PUT /api/user/123
          DELETE /api/user/123
          PATCH /api/user/123
```

#### 4b. Parameter Pollution

```
# Duplicate parameters (the server may take the first or the last)
GET /api/profile?id=YOUR_ID&id=VICTIM_ID
GET /api/profile?id=VICTIM_ID&id=YOUR_ID

# Path + parameter mixing
GET /api/user/YOUR_ID?user_id=VICTIM_ID
```

#### 4c. Encoding Bypass

```
# Original ID
?id=123

# Try different encodings
?id=MTIz          # base64
?id=%31%32%33     # URL encoded
?id=0x7B          # hex
?id[]=123         # array notation
{"id": "123"}     # JSON string vs int
{"id": 123}
```

#### 4d. Version Substitution

```
# An older API version may lack an ownership check
/api/v1/user/123   <- may have IDOR
/api/v2/user/123   <- may already be fixed
/api/v3/user/123   <- current version (protected)
```

#### 4e. Content-Type Substitution

```
# If the JSON endpoint is protected, try other formats
Content-Type: application/json     <- protected
Content-Type: application/xml      <- may not be protected
Content-Type: multipart/form-data  <- may use a different parser
```

### Phase 5: Dual-Account Cross-Verification (mandatory)

> ⚠️ **After hitting a generic "not found" exception, Phase 5 is mandatory** — otherwise the result may be a false positive.

```
Account A (attacker): obtain Bearer Token A
Account B (victim): create a resource, obtain Resource ID B

Test: access Resource ID B using Token A
- 200 + B's data -> ✅ IDOR confirmed
- 403 / an "invalid customer" style exception -> ❌ false positive
```

## Decision Points

### Common IDOR scenarios

**Order IDOR**

```
POST /api/orders/view
{"orderId": 12345}

# change to
{"orderId": 12346}
```

**Profile-read IDOR**

```
GET /api/users/profile?userId=100
# change the userId value
```

**File-download IDOR**

```
GET /download?file=user100_invoice.pdf
# change to
GET /download?file=user101_invoice.pdf
```

**GraphQL IDOR**

```graphql
# Using a nodes() or node() resolver
query {
  node(id: "OTHER_USER_RELAY_ID") {
    ... on User { email phone }
  }
}
```

### Burp Intruder for batch testing

```
1. Find a request containing an ID, Send to Intruder
2. Select the ID value, mark it with §
3. Payloads -> Numbers (sequential) or a list of known IDs
4. Fire
5. Sort responses by "Length" -- an outlier length usually means a response containing data
```

### Severity assessment

| Type | Severity |
|------|----------|
| READ: view another user's data (PII) | Medium-High |
| READ: view another user's financial data | High |
| WRITE: modify another user's data | High |
| WRITE: delete another user's data | High |
| WRITE: cancel another user's order | High |
| WRITE: bypass payment | Critical |

### Per-Verb Testing Checklist

> **Rule: every IDOR endpoint must be tested against all 5 HTTP verbs**, not just GET. A real-world case awarded a five-figure bounty specifically because the reporter kept going past GET into PUT/DELETE on the same endpoint.

#### Required test matrix

| Endpoint | GET | POST | PUT | PATCH | DELETE |
|----------|-----|------|-----|-------|--------|
| `/api/users/{id}/profile` | read PII | create | **modify anyone's profile** | **mass assignment** | **no confirmation = Critical** |
| `/api/users/{id}/settings` | read API key | -- | modify settings | -- | reset settings |
| `/api/orders/{id}` | read order | -- | modify order | -- | cancel order |
| `/api/files/{id}` | download | -- | replace file | -- | delete file |

#### What actually drives a severity upgrade

| Signal | Upgrade to |
|--------|-------------|
| READ IDOR | Default **Medium/High** |
| + contains PII / financial data | **High** |
| + mass-enumerable (a sequential ffuf sweep) | **CVSS Scope:Changed -> Critical** |
| WRITE IDOR | Default **High** |
| **DELETE with no confirmation / no re-auth** | **Critical** (irreversible + no confirmation) |
| WRITE + cross-tenant | **Critical** |

#### Mass-enumeration PoC (do this)

```bash
# Use ffuf to demonstrate bulk exfiltration -- this is what pushes a single IDOR to Critical
ffuf -u "https://target.example.com/api/v2/users/FUZZ/profile" \
     -H "Authorization: Bearer YOUR_TOKEN" \
     -w numbers.txt \
     -mc 200 \
     -of json -o idor_results.json

# Count results
jq '.results | length' idor_results.json
```

In the report, state something like: "retrieved 47 complete user profiles (email + phone + billing) in under 30 seconds" — the CVSS Scope:Changed rationale then makes itself.

#### Extra checks for destructive verbs

For DELETE / large UPDATE operations, confirm:
- [ ] Does it require password re-entry?
- [ ] Does it require 2FA / OTP confirmation?
- [ ] Is there a confirmation token (bound like a CSRF token)?
- [ ] Does it send an email notification + an undo link?

**Any "No" answer** = emphasize "irreversible action without re-authentication" in the report as the Critical-severity driver.

#### Swagger / OpenAPI is a goldmine

Check these paths on every target **first**:
```
/swagger
/swagger-ui
/swagger.json
/openapi.json
/api-docs
/v2/api-docs
/v3/api-docs
/api/swagger
/docs
/api/docs
/redoc
/graphql        # GraphQL ships its own introspection
```

A spec gives you every endpoint + parameter + verb directly — roughly 10x faster than fuzzing.

### When Burp isn't needed

Burp is **not required** for:
- GraphQL — curl works directly
- REST APIs — curl + jq works directly
- Documented endpoints with a Swagger/OpenAPI spec — read the spec directly

Burp is most useful for:
- SPAs (React/Vue/Angular) — inspect XHR/Fetch directly
- Encrypted/obfuscated requests — intercept the decrypted version in Burp
- Cookie-based auth — automatically carries cookies

## Expected Outputs

- A confirmed IDOR list (endpoint, ID type, verb, response evidence) with severity assigned per the table above.
- A dual-account cross-verification record for every finding that first surfaced as a generic "not found" exception.
- A mass-enumeration PoC (ffuf output + count) for any READ IDOR being escalated toward Critical.
- A documented negative-result list for endpoints that returned 403 / correctly scoped errors.
